Background jobs look simple until reliability matters.

Once a worker can retry, crash, or process the same message twice, the system needs explicit guarantees around idempotency, failure handling, and observability.

## Why background jobs need stronger guarantees

A request-response API can usually communicate success or failure directly to the caller.

Background work is different.

A queue may redeliver a message, a worker may crash after the side effect but before acknowledging the message, and downstream services may become temporarily unavailable.

The result is that a job handler should not assume it will execute exactly once.

In practice, designing for at-least-once delivery and making handlers safe to repeat is usually the more useful mental model.

## Idempotency as the first line of defense

The most important property of a retryable job is idempotency:

> Executing the same logical operation multiple times should produce the same intended result.

One practical approach is to associate every logical job with an idempotency key and persist the processing state alongside the side effect.

```ts
const job = await jobs.findById(jobId);

if (!job) {
  throw new Error("Job not found");
}

if (job.status === "completed") {
  return;
}

await processJob(job);

await jobs.markCompleted(job.id);
```
